## Стек и обоснование

| Компонент | Технология | Почему |
|---|---|---|
| API | FastAPI + Pydantic 2 | Схемы правил и документов валидируются на границе |
| БД | PostgreSQL 16, SQLAlchemy 2, Alembic | Версии неизменяемы; процесс ссылается на версию |
| Процессы | Явная машина состояний (`transitions` или своя) + Celery для таймеров | Temporal — после MVP, когда появятся долгие A1-окна |
| Документы | Jinja2 → docxtpl → DOCX → PDF через LibreOffice headless | Детерминированно, LLM не касается текста |
| Воркеры | Celery + Celery Beat (Redis брокер) | Ежедневный мониторинг сроков, ежемесячное начисление |
| Аудит | Таблица `audit_log`, хеш-цепочка, роль БД без UPDATE/DELETE | «Append-only» должно быть доказуемым |
| ПДн | Шифрование колонок (`pgcrypto` или app-level, ключ на тенанта) + MinIO для файлов | Уничтожение ключа = уничтожение данных |
| Кабинет | Next.js 14, TypeScript, shadcn/ui | Быстрый кабинет, типизация контрактов API |
| Инфра | Docker Compose: postgres, redis, minio, api, worker, beat, frontend, soffice | Один `docker compose up` на стенде |

## Ключевой инвариант

**Инструменты агента (этап 3), таймеры воркеров и экраны подтверждения генерируются
из одного реестра правил.** Правило объявляет: триггер, действие, параметры, уровень
автономии. Если A2 — действие получает только `prepare()`, а `execute()` вызывается из
очереди решений. Если A3 — правила в реестре исполняемых действий нет вообще.

## Модель данных (ядро)

```
organizations            — тенант, настройки автономии (только ужесточение)
users                    — роль: director | hr | employee
employees                — ФИО, должность, оклад, даты; ПДн — в encrypted-колонках
employee_documents       — паспорт, СНИЛС, ИНН, военный билет…  (encrypted)
rules / rule_versions    — имя, версия, триггер, действие, params(jsonb), autonomy, norm, verified_by/at
templates / template_versions — код формы (T-1…), поля, docx-файл
processes                — type, state, employee_id, rule_version_ids(jsonb), started_at
process_events           — переходы состояний
decisions                — очередь A2: process_id, action, payload, status, decided_by/at
generated_documents      — process_id, template_version_id, pdf/docx path, signed_at (имитация)
obligations              — тип отчёта, получатель, deadline, due_kind(calendar|working), status, autonomy
report_packages          — сформированный пакет, результат валидации, квитанция заглушки
vacation_balances        — начисления по месяцам, остаток
production_calendar      — год, дата, тип (holiday|shortened|transfer), источник
audit_log                — ts, actor(kind,id), rule_version_id, action, payload_ref, prev_hash, hash
```

## Поток данных: приём на работу (MVP, ручной ввод)

```
1. Кадровик: форма «Новый приём» → candidate + hiring_request          (A0)
   → проверка штатного расписания → warning в контекст
2. Кадровик вводит документы кандидата (паспорт, СНИЛС, ИНН…)
   → валидаторы: контрольные суммы, срок паспорта, совпадение ФИО
   → расхождение → задача кадровику, процесс ждёт
3. Проверки перед оформлением                                           (A0)
   age · foreign_citizen · military_duty · former_civil_servant · medical_exam
   → стоп-фактор → state=blocked, задача руководителю
   probation_period_limits → см. 04-DOMAIN-NOTES (исполнять ВСЕ категории)
4. Согласия (ПДн, КЭДО, способ ведения ТК) — отмечает кадровик по бумажным/скан
5. Сборка пакета из шаблонов → generated_documents (draft)            (A0)
   договор, Т-1, согласия, Т-2, лист ознакомления, [договор о МО]
6. decisions: employment_contract_signing                              (A2)
   руководитель видит условия + результаты проверок → «подписать» (имитация ЭП)
7. После подписания:
   → decisions: hiring_order_t1                                         (A2)
   → military_registration_internal                                     (A0)
   → vacation_accrual start
   → timer: probation_end − 5 дней
   → obligations: efs1_1_1_hiring (след. раб. день), [mvd_hiring 3 раб. дн],
     [military_office 5 кал. дн], [former_civil_servant 10 кал. дн]
8. Воркер обязательств → формирует пакет → валидация → заглушка ЭДО → квитанция (A1,
   но в MVP: первая отправка каждого вида и первые 30 дней = A2 → очередь решений)
```

Каждый шаг пишет в `audit_log`: actor, rule_version_id, action, ссылка на payload.

## Расчёт дат — единая библиотека `app/calendar`

- `add_calendar_days(d, n)`, `add_working_days(d, n)` по production_calendar
- `add_months(d, n)` — календарные месяцы, конец месяца → последний день
- `next_working_day(d)`, `is_working_day(d)`
- Исчисление «со следующего дня» — отдельный флаг, **по умолчанию как в реестре**
  (расхождение C4 — не исправлять до вердикта юриста, но реализовать как опцию)
- Все расчёты сроков в системе идут только через этот модуль. Тесты обязательны.
